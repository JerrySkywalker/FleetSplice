# R02/R05 — Paseo plugin and upstream boundary

Pins: Paseo `v0.11.2@75953250959979b8f088bbca8dbd6ee61d0151b1` and HEAD `0708b8295c102d1d5ea5acbfa512691c7d0e19ba`; relevant SDK/Codex/timeline files have no release-to-HEAD diff. Conclusions below are source facts or labeled designs, not a functional plugin claim.

## What the documented API permits

[`@getpaseo/plugin/server/provider`](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/plugin/src/server/provider.ts#L28) exposes `ProviderRegistration { id, label, command?, status?, connect }`; `connect` negotiates version/capabilities and returns `ProviderConnection { send, onEvent, close }`. `ProviderSessionConfig` carries cwd, environment, model, mode, thinking option, settings and persistence. Supported inputs/events include session open/prompt/configure/interrupt/permission, lists, timeline items and persistence. The [direct-provider example](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/plugin-examples/provider-direct/server/provider.ts#L1) proves a custom provider can implement the protocol, not that it can adopt an external Codex Writer.

The [plugin guide](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/docs/plugins.md#L397) supports provider registration, lifecycle observers/transforms, client surfaces, timeline item renderers and daemon RPC. The plugin subprocess is trusted and unsandboxed with daemon-user file/process/credential/network access; install/update and per-Host copies are a security and operations cost. Reload/disable closes plugin connections and subprocess; a provider for an external process must ensure its own `close` only drops its client socket/subscription, never kills or archives a process it did not create. This is a plugin implementation rule, not a guarantee supplied by the SDK.

The existing [Paseo Codex adapter](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/server/src/server/agent/providers/codex-app-server-agent.ts#L7226) repeatedly spawns stdio `codex app-server` for create/resume/import/catalog; [`thread/resume`](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/server/src/server/agent/providers/codex-app-server-agent.ts#L4060) takes Native Writer in that child, while [session close](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/server/src/server/agent/providers/codex-app-server-agent.ts#L5026) disposes it. [AgentManager](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/server/src/server/agent/agent-manager.ts#L1448) registers imported sessions and owns timeline/lifecycle. A plugin registered as a *new provider* can bypass this Codex adapter; it cannot silently replace the built-in Codex Agent semantics or its already-stored Agent IDs.

## Narrow candidate, and the exact missing proof

One possible B2 prototype would register `codex-external` as a separate provider. Its `status` would observe only an official, validated shared daemon endpoint. `connect` would attach through a documented Codex client transport, list a pre-existing Native Thread, subscribe to live events and derive exact thread/turn/permission IDs. It would never start a second Writer or claim process ownership. `session.prompt` and `session.permission` would be admitted only after verifying same daemon incarnation, loaded thread, observed native state and a cooperative controller fence; ambiguous sends become explicit unknown receipts. `close` would close its own connection only.

This is **not implemented or proven**. The public SDK describes provider events; it does not provide a ready-made official daemon discovery/identity validator, a native multi-client Writer/fence protocol, a cross-client atomic compare-and-submit token, or a daemon-owned receipt journal. Codex [Writer locking](https://github.com/openai/codex/blob/6fbd7be1518d259e30e6fef48f05f433d2461a20/codex-rs/rollout/src/writer_lock.rs#L42) and [shared daemon eligibility](https://github.com/openai/codex/blob/6fbd7be1518d259e30e6fef48f05f433d2461a20/codex-rs/tui/src/startup_orchestration.rs#L189) are upstream facts that no plugin can override. On this ZenBook, [current FS status](../../../train/current-status.md) reports the official managed daemon cannot detach; a source-only plugin cannot turn the present unwrapped embedded process into a shared app-server. Any private socket scraping or Writer lock deletion would violate the study boundary.

Even if the above external-native provider later works on a qualified Host, it enters [Paseo's in-memory `AgentManager.timelineStore`](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/server/src/server/agent/agent-manager.ts#L744). [The store](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/packages/server/src/server/agent/agent-timeline-store.ts#L34) keeps all projected rows; its `fetch` pages a copied full array. Public timeline renderers/appended items do not replace daemon storage, client cache, global timeline state or virtualized history. Fixing G08's bounded-residency P0 therefore crosses a core server/client boundary.

## Classification and replacement cost

| Route/component | Boundary | Deletion/replacement and maintenance cost |
| --- | --- | --- |
| B1 configured existing Codex provider | `CONFIG_ONLY`: command/env/model and Host selection; works for Paseo-managed Agents | Low ongoing code cost; changes Owner startup workflow and cannot repair history residency. |
| B2 distinct external-native provider | `PLUGIN_ONLY` **only for protocol mapping and app integration** if shared Codex endpoint exists; `UNSUPPORTED_OR_UPSTREAM_NATIVE_BLOCK` on embedded/`--no-daemon` or unusable Windows daemon | Own discovery, native version drift, Writer/fence, receipt semantics, multi-Host installation and plugin trust. Deleting plugin removes its live Agent integration; native transcripts remain native but Paseo-specific Agent IDs/settings need migration. |
| B3 bounded Paseo contribution | `SMALL_UPSTREAM_CHANGE` may add explicit external-process custody or a connection-only Codex transport; no accepted patch exists. G08's bounded timeline and client cache/DOM changes are **multiple core subsystems**, so not honestly one small patch. | Track maintainer review and released version; requalify Windows, reconnect and history on each relevant release. Absent acceptance, patch becomes B4. |
| B4 private fork | `LONG_LIVED_FORK`: replaces built-in Codex path plus server timeline, client history and potentially relay byte planning | Highest merge burden against frequent Paseo changes; fork is a product, not a plugin. Compare fully against independent FS. |
| Native `--no-daemon`/elevated or no reachable shared endpoint | `UNSUPPORTED_OR_UPSTREAM_NATIVE_BLOCK` for A, B and C alike | Needs an upstream Codex/Windows solution or an Owner-approved workflow change; no client-side fork solves the inaccessible Writer. |

Paseo's custom client UI and plugin RPC can present a separate page or display but cannot change core timeline residency merely by installing a renderer. The source-supported external provider gives B2 a **possible narrow native experiment on a qualified shared-daemon Host**, not a P0 PASS on this ZenBook.

## R05 `SPIKE_RESULT`

`PLUGIN_API_INSUFFICIENT; SKIPPED_SOURCE_DECISIVE`. A type-only `ProviderRegistration` mock would merely restate the public `send/onEvent/close` contract already demonstrated by [the upstream direct example](https://github.com/getpaseo/paseo/blob/0708b8295c102d1d5ea5acbfa512691c7d0e19ba/plugin-examples/provider-direct/server/provider.ts#L1). It could not test the missing official shared endpoint/Writer on ZenBook or replace `AgentManager`'s timeline store. Running it would create a false confidence signal. No plugin installed, dependency built, Codex process started or source modified. A later pilot is justified only after the Owner admits a qualified shared native endpoint and the intended P0 is still unmet.

## Topology and authority flow

Client → direct Daemon WebSocket → AgentManager → native provider process and provider history. An optional encrypted Relay can bridge client↔Daemon when direct reachability is unavailable. Separately, Daemon may register itself outbound to a Hub for organization/trigger workflows. [Hub relationship](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/docs/hub.md) explicitly says enrollment is opt-in, relay is not used for Hub enrollment or dispatch, Hub connection has no daemon permissions by default, and hub.execute must be granted for workflow execution. Hub is therefore neither mandatory for single-Host client traffic nor automatically authorized to run agents. The Hub identity, Daemon relationship credential, and human login differ.

SOURCE_FACT: the Daemon/AgentManager is the Paseo-side lifecycle owner; the native provider remains authority for its own transcript and actual effects. Daemon Timeline rows are a projected in-memory view. [Timeline design](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/docs/timeline-sync.md) describes source sequence and epoch, fetched projected pages, after-cursor gap repair and provider-history rehydration on resume. A live stream is for responsiveness; fetch_agent_timeline_request is the correctness path. Tool output is capped at 64 KiB in the canonical projection and live event. This byte cap limits display transport; it does not prove full native history is stored by Paseo.

Create intent handling and [creation idempotency e2e](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/packages/app/e2e/browser/creation-idempotency.spec.ts) are counterexamples to a blanket claim that only FS considers duplicates. Their existence does not prove every submit, steer, interrupt and approval is safe after an indeterminate native response. That requires command-specific fault injection.

## Performance paths

Semantic Agent path: provider event → AgentManager → [AgentStreamCoalescer](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/packages/server/src/server/agent/agent-stream-coalescer.ts) → WebSocket client → [frame-batched reducer](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/packages/app/src/timeline/session-stream-reducers.ts) → paced reveal → UI. The coalescer constant is 60 ms; leading flush avoids a full-window first-delta delay and trailing flush reduces sustained message rate. [Stream document](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/docs/agent-stream-performance.md) reports its own smoothness measurements, which are Paseo-only, not cross-product evidence.

Terminal path: native PTY → worker/headless xterm → leading/trailing output coalescer around 5 ms → IPC → daemon binary WebSocket → client emulator. [Terminal document](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/docs/terminal-performance.md) says snapshot catch-up is gated when output since snapshot exceeds 256 KiB AND transport bufferedAmount exceeds 4 MiB. Terminal parsing, snapshots, IPC and optional relay encryption consume resources unavailable in a semantic-chat-only FS comparison. Benchmark terminal as a separate capability track.

## Contrast with FS and limits

Paseo already covers a Host-local Daemon, multi-device reach, optional Hub, lifecycle management, structured Agent stream coalescing, bounded paged Timeline repair and terminal backpressure. These are concrete counterexamples to an FS uniqueness claim. FS's candidate distinction is its explicit central Fleet logical authority, Host/Environment/Workspace separation, durable Hub intent plus Edge attempt and no-blind-replay rule; [FS authority](../../../architecture/authority-model.md). Whether that gives a useful correctness or resource advantage is UNKNOWN. FS also pays an always-on Hub for its specified remote path, whereas Paseo direct clients need no Hub. Per-Host Daemon/Edge resource numbers and total topology cost are UNKNOWN.

Importing a persisted Codex session is supported by source; exact same-writer control of an externally active native TUI and remote steering semantics are UNKNOWN without a current targeted test. A Codex active-thread refusal mentioned in [timeline design](https://github.com/getpaseo/paseo/blob/b58af43a0675f2cd83d7b44489dd6cb58da79268/docs/timeline-sync.md) is a scenario boundary, not a global statement that all imports fail. No source here proves Paseo owns or can arbitrate an external native writer. Conversely, no source proves FS currently does so with Codex 0.162.1.
